## 1. 图像生命周期与所有权

解释本项目中图像源为什么会复用缓冲区，以及 `cv::Mat` 的普通复制对底层像素数据
意味着什么。说明你的修改让一个 `Frame` 在进入队列后拥有什么，并解释为何后续读取
不会再改变它。

图像源通过 `raw.copyTo(buffer_)` 模拟相机复用内部缓冲区的行为。当图像尺寸和类型
相同时，可以重复使用已经分配的像素内存，减少每帧重新分配内存的开销。

原来的 `frame.image = buffer_` 是浅拷贝，只复制 `cv::Mat` 的头部并共享底层像素数据。
引用计数能保证这块内存在仍被引用时不会释放，但不能阻止图像源覆盖其中的像素。
因此，producer 读取下一帧时，队列中尚未处理的帧或 worker 正在读取的帧可能发生变化，
导致校验失败，甚至出现像素读写的数据竞争。

修改为 `frame.image = buffer_.clone()` 后，每次读取都会复制像素，得到独立于图像源
缓冲区的存储。入队的 Frame 持有这份像素数据的引用；即使入队时再次浅拷贝 Frame，
引用计数也会维持其生命周期。下一次读取只会修改图像源的缓冲区，不会修改已经入队
的像素数据，因此 worker 可以安全地处理对应帧。

## 2. 并发处理与恰好一次

结合 `BlockingQueue` 的 `push`、`pop` 和 `close` 行为，解释多个 worker 如何分工。
为什么你的实现既不会漏掉已经入队的帧，也不会重复处理同一帧？输入耗尽时，正在等待
以及仍在处理数据的 worker 分别会怎样？

producer 使用 `push()` 将每帧加入共享队列，并唤醒一个等待的 worker。每个 worker
在循环中调用 `pop()`，取得一帧后释放队列锁，再进行图像处理，所以多个 worker
可以并行处理不同的帧。

`pop()` 在同一把互斥锁保护下取出队首元素并将其移除，因此同一帧只能被一个 worker
取到，不会重复分配。producer 在所有帧入队后才调用 `close()`；关闭队列只设置关闭
标志并唤醒所有等待者，不会丢弃剩余元素。因此，在读取、处理和保存正常完成的前提下，
所有已入队的帧都会被取出并处理一次。

队列暂时为空但尚未关闭时，worker 会通过条件变量等待新帧。输入耗尽并关闭队列后，
等待中的 worker 被唤醒：如果还有帧就继续取出，如果队列为空就退出。正在处理的
worker 会先完成当前帧，再继续取剩余帧。只有队列已关闭且为空时，`pop()` 才返回
false，使 `workerLoop()` 结束。线程结束后，其 `std::thread` 对象仍然 joinable，
由 `wait()` 或析构函数中的 `join()` 完成回收。


## 3. 共享统计数据

指出哪些线程会读写 `Statistics`。解释原实现中的竞争为什么可能导致错误结果，并说明  
你的同步方案提供了什么保证。还应说明取得快照时为什么是安全的。 

一个 producer 通过 `onProduced()` 更新生产计数；多个 worker 通过 `onProcessed()`、
`onSaved()` 和 `onCorrupted()` 更新处理、保存及损坏计数。worker 的数量由配置决定，
默认是三个。调用者通过 `snapshot()` 读取这些计数。

原实现中的加一需要先读取旧值，再计算并写回新值，并不是一个不可分割的操作。
例如两个 worker 都读到 processed 为 10，随后都写入 11，处理了两帧却只增加一次。

当前实现用同一把 `statistics_mutex` 保护所有更新函数。`std::lock_guard` 从读取旧值
到写回新值一直持有锁，使更新操作依次执行，避免更新丢失，并在函数退出时自动释放锁。
这把锁位于源文件的匿名命名空间中，因此不同 Statistics 实例的更新也共用它。

当前 `snapshot()` 没有加锁，所以安全读取的前提是所有更新线程已经结束。调用者在
`wait()` 返回后取快照时，所有线程都已 `join()`，线程中的写入对调用者可见，而且
不再有并发写入，因此读取是安全的。如果需要在流水线运行期间取得快照，就必须让
`snapshot()` 也持有同一把锁，才能避免读写竞争，并保证四个计数在读取过程中不变。

## 4. 线程关闭协议

分别描述以下两条路径中的事件顺序，并解释为什么不会发生 `std::terminate`、悬空访问
或永久等待：

1. 调用者执行 `start()` 后显式调用 `wait()`；
2. 调用者执行 `start()` 后不调用 `wait()`，直接让 `Pipeline` 析构。

如果你的实现允许某个生命周期方法被重复调用，也请说明其行为；如果不允许，请说明前置条件。

1. 显式调用 `wait()` 时，先执行 producer 的 `join()`，等待它读完输入并调用
   `queue_.close()`。关闭队列会唤醒等待中的 worker，但不会清空已经入队的帧。
   worker 继续取出并处理剩余帧，直到队列已关闭且为空时，`pop()` 返回 false，
   `workerLoop()` 结束。随后 `wait()` 对每个 worker 执行 `join()`，确保所有线程都已结束。

2. 不调用 `wait()` 而直接析构时，析构函数先等待 producer 结束，再调用
   `queue_.close()`，最后等待所有 worker 结束。这是等待全部任务完成，并不是立即取消任务。
   producer 已经关闭过队列时，再次关闭也不会产生问题。

两条路径都会在成员销毁前完成线程的 `join()`，因此不会因为销毁仍然 joinable 的
`std::thread` 而触发 `std::terminate`。线程使用的 `source_`、队列和统计对象等成员
在析构函数执行期间仍然有效，线程结束后才销毁这些成员，所以不会产生悬空访问。
在输入有限、读取和处理正常返回且线程函数没有未捕获异常的前提下，producer 最终会关闭
队列，等待中的 worker 会被唤醒，剩余任务处理完后全部退出，因此不会永久等待。

`wait()` 可以由调用者顺序重复调用，因为已经 `join()` 的线程不再 joinable，会被跳过；
调用过 `wait()` 后再析构也一样。`start()` 的前置条件是每个 Pipeline 对象只调用一次，
生命周期方法由外部调用线程顺序执行。当前实现没有重置队列或线程的机制，不能用同一对象
重新启动；第一次启动后尚未 `join()` 就再次启动，还会因覆盖 joinable 的 producer 线程对象
而触发 `std::terminate`。
